## 중간 표본의 원래 파일명으로 발생한 413

원래 이름 `데이터 분석을 위한 파이썬 및 상용 클라우드 서비스를 활용한 애플리케이션 운영.pdf`로 전송했을 때 0.043초 만에 HTTP 413 `FILE_TOO_LARGE`가 반환됐다. 그 요청에 대응하는 Backend → AI 호출 로그는 없었다. 원본과 SHA-256이 같은 사본을 같은 클라이언트에서 `medium.pdf`로 전송하자 성공했다. 이 결과는 전송 파일명에 따라 동작이 달라졌음을 보여준다. 거절을 일으킨 헤더나 서버 제한은 확인하지 못했다.

## 검증 근거

- 클라이언트 전체 시간은 업로드 직전부터 응답 수신 직후까지 Stopwatch로 측정했다. 내부 시간은 Backend의 HTTP POST 시작과 Reactor Netty의 응답 본문 수신 완료 기록을 사용했다. 내부 요청은 모두 HTTP 200이었다.
- Backend의 내부 시작 → 완료 시각은 소형 23:47:30.459 → 23:47:31.220, 중간 23:48:21.091 → 23:48:28.716, 대형 23:47:45.591 → 23:47:49.941이다.
- MariaDB에서 세 문서 행의 파일 크기와 READY 상태를 직접 확인했다. Chroma는 DB에서 얻은 소유자 UUID와 개별 문서 ID로 조회했고, 각 고유 청크 수가 로컬 전처리 결과와 일치했다.
- 세 성공 요청 모두 Backend → AI 120초 기준을 충족했다. 223페이지 중간 표본이 38페이지 대형 표본보다 오래 걸렸다. 각 표본의 성공 측정은 1회이며, 파싱·임베딩·저장 단계별 시간은 측정하지 않았다.
- 같은 대형 PDF의 [첫 적재 기록](large-pdf-ingestion.md)은 전체 5.315초, 내부 5.057초였다. 위 표의 대형 행은 이번 비교에서 새 문서로 업로드한 결과다.
