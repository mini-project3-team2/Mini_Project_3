## 2. 프로젝트 구조

```
frontend/
├── src/
│   ├── main.jsx        # MSW 시작(개발 전용) → 토큰 복원(restore) → 렌더링
│   ├── App.jsx         # 라우트 정의
│   ├── index.css       # Tailwind, 디자인 토큰(@theme)
│   ├── pages/          # LoginPage, SignupPage, ChatPage, DocumentsPage, HistoryPage
│   ├── components/     # AppLayout, ProtectedRoute(GuestRoute), AuthCard, FormAlert, ErrorIcon,
│   │                   # LoadingSpinner, ChatInput, ChatMessage, SourceCard, FeedbackButtons,
│   │                   # FeedbackChip, feedbackStyle.js, FileUploader, DocumentList, StatusBadge,
│   │                   # HistoryItem, Pagination
│   ├── services/       # api.js(axios · 401 재발급), chatStream.js(fetch + SSE 파서)
│   ├── store/          # authStore, chatStore, documentStore, historyStore (Zustand)
│   ├── hooks/          # useChatStream, useDocuments, useHistory
│   ├── utils/          # errorMessage(오류 문구 · 날짜), validate, refusal(거절 답변 판정), format
│   └── mocks/          # MSW 핸들러 (개발 전용, 운영 빌드에서 제외)
├── public/             # favicon.svg, mockServiceWorker.js(개발 전용)
├── vite.config.js      # /api 프록시, MSW 워커 제외 플러그인
├── nginx.conf          # 정적 파일 서빙, /api 프록시, 보안 헤더
├── Dockerfile          # node 빌드 → nginx 실행
└── package.json
```

- API 호출 · 토큰 재발급은 `services/` 한 곳에서만 한다. 화면 · 스토어는 `services/`의 함수만 부른다
- `mocks/`는 `mock-data/`(팀 공통 응답 · SSE 예시)를 그대로 읽어 쓴다 (`vite.config.js`의 `server.fs.allow`)

## 3. 환경 설정

```env
VITE_API_URL=/api
VITE_USE_MOCK=false
```

| 변수 | 용도 | 비고 |
|------|------|------|
| `VITE_API_URL` | API 기본 경로 | 개발 · 운영 모두 상대경로 `/api`. 개발은 `vite.config.js` 프록시로 `http://localhost:8080`, 운영은 Nginx가 `backend:8080`으로 전달. Docker 빌드는 Dockerfile의 `ARG VITE_API_URL=/api` 기본값 사용 |
| `VITE_USE_MOCK` | MSW 사용 여부 | `true`이고 개발 서버일 때만 동작 |

> `VITE_` 접두사 변수는 **빌드 결과물에 그대로 노출**된다. API 키 · 비밀번호를 넣지 않으며, 현재 변수는 위 2개뿐이다.
> AI 모듈은 Backend를 통해서만 호출하며, 브라우저에서 직접 호출하지 않는다 (화면은 `/api`만 호출).

### 3.1 MSW 개발 환경

| 항목 | 내용 |
|------|------|
| 켜기 · 끄기 | `VITE_USE_MOCK=true`로 `npm run dev` 실행 시에만 워커 시작 (`main.jsx`: `import.meta.env.DEV` 확인). Backend에 붙일 때는 `false` |
| 운영 빌드 제외 | `main.jsx`의 조건 때문에 운영 번들은 MSW를 시작하지 않음. `public/`에서 복사되는 `mockServiceWorker.js`는 `vite.config.js`의 `dropMockWorker` 플러그인(`apply: 'build'`)이 빌드 후 `dist/`에서 삭제 |
| 핸들러 | `mocks/handlers/` — auth(가입 · 로그인 · 재발급 · 로그아웃), documents(목록 · 업로드 · 삭제), chats(기록 · 피드백 · 스트리밍), rateLimit(429 재현) |
| mock 데이터 | `mock-data/data/*.json`을 초기값으로 쓰고, 변경 내용은 sessionStorage `msw:db`에 보관 (탭을 닫으면 초기화). mock 토큰은 JWT 형태가 아닌 값 사용 |

**429 재현 방법** (`mocks/handlers/rateLimit.js`, 개발 mock 전용)

1. `VITE_USE_MOCK=true`로 개발 서버 실행 → 로그인
2. 브라우저 콘솔에서 `sessionStorage.setItem('mock429', 'html')` 입력
   - `html`: Nginx 기본 HTML 본문 → 화면 기본 문구
   - `json`: 공통 실패 형식 + `message` → 서버 문구
   - `empty`: 공통 실패 형식, `message` 없음 → 화면 기본 문구
3. 아무 API 호출 → 429 문구 확인 (`/auth/refresh`는 제외해 새로고침해도 로그아웃되지 않음)
4. `sessionStorage.removeItem('mock429')`로 끄기

## 4. 주요 페이지

| 경로 | 컴포넌트 | 기능 |
|--------|----------|------|
| `/login` | `LoginPage` | 로그인. 가입 완료 · 세션 만료 안내, 잠금(423) 시 해제 시각 표시. 비로그인 전용(`GuestRoute`) |
| `/signup` | `SignupPage` | 회원가입. 이메일 · 비밀번호 규칙 · 비밀번호 확인 검사 후 가입 → `/login`으로 이동. 비로그인 전용(`GuestRoute`) |
| `/chat` | `ChatPage` | AI 학습 채팅. 답변 스트리밍, 근거 자료, 피드백, 중단. 자료 상태별 첫 화면(자료 없음 · 적재 중 · 예시 질문) |
| `/documents` | `DocumentsPage` | 내 자료. PDF 업로드(선택 · 드래그 앤 드롭), 목록(상태 · 크기 · 업로드 시각), 삭제 확인 |
| `/history` | `HistoryPage` | 질문 기록. 페이지 목록(`?page=N`, 1부터), 긴 답변 접기, 근거 자료 · 피드백 표시(읽기 전용) |
| `*` | `Navigate` | `/chat`으로 이동 |

- `/chat` · `/documents` · `/history`는 `ProtectedRoute` → `AppLayout`(상단 헤더 + 본문) 안에서 열린다
- `GuestRoute`는 로그인 상태면 원래 가려던 주소(`state.from`)로 보낸다. `/`로 시작하고 `//`로 시작하지 않는 값만 허용하고, 그 밖에는 `/chat` (다른 사이트로 이동 방지)

## 6. 상태 관리

| 스토어 | 설명 |
|--------|------|
| `authStore` | `setAuth`(토큰 · 회원 저장, Refresh는 sessionStorage), `clear`(모두 삭제, `expired`로 세션 만료 안내), `setReady`(복원 완료) |
| `chatStore` | 메시지 `status`: `waiting`(첫 이벤트 전) → `streaming` → `done` / `error` / `stopped`(중단 버튼 · 메뉴 이동). 메뉴를 이동해도 유지 |
| `documentStore` | 목록 · 업로드 · 삭제 상태. 업로드 요청은 스토어에서 진행하므로 화면을 떠나도 계속됨 |
| `historyStore` | 현재 페이지 데이터. 화면을 떠나면 비움 (`useHistory`) |

- 훅: `useChatStream`(질문 전송 · 중단), `useDocuments`(화면 진입 시 목록 다시 불러오기), `useHistory`(페이지 변경 시 다시 불러오기)
- `documentStore` · `historyStore`는 `seq`로 늦게 온 이전 요청 응답을 무시한다 (빠른 페이지 이동 · 연속 요청)

스토어별 상태 필드는 다음과 같다.

```javascript
// Zustand (persist 미사용 — 새로고침하면 메모리 값은 사라짐)
{
  auth:     { accessToken, member, ready, expired },        // Refresh Token은 sessionStorage 'refreshToken'
  chat:     { messages: [{ id, question, answer, sources, chatId, feedback, status, error }] },
  document: { items, loadError, uploading, uploadError, deletingId, actionError, notice },
  history:  { data, loading, error }                         // data = 페이지 응답, PAGE_SIZE 10
}
```

## 7. API 연동

| 항목 | 내용 |
|------|------|
| HTTP 클라이언트 | `services/api.js`의 axios 인스턴스 (`baseURL` = `VITE_API_URL`, `timeout` 60000ms) |
| 응답 형식 | `{success, data, message, code}` (`code`는 실패 시에만 포함) |
| 인증 헤더 | 요청 인터셉터가 메모리의 Access Token을 `Authorization: Bearer`로 붙임 |
| 401 처리 | 응답 인터셉터: 401 → 재발급 1회 → 원래 요청 재시도 |
| 인증 함수 | `login` · `signup` · `logout` · `refresh` · `restore`(새로고침 시 Refresh로 복원) |
| 자료 함수 | `getDocuments` · `uploadDocument`(`multipart/form-data` 필드 `file`, 180초) · `deleteDocument` |
| 채팅 함수 | `getChats(page, size)` · `sendFeedback(chatId, feedback)` (`api.js`), `streamChat(question)` (`chatStream.js`) |

- 경로 변수는 `encodeURIComponent`로 넣는다. 소유자 uuid · 회원 id는 요청에 넣지 않는다 (서버가 JWT로 판단)

### 7.1 SSE 스트리밍 처리

`EventSource`는 POST · `Authorization` 헤더를 쓸 수 없으므로 `fetch` + `ReadableStream`으로 읽는다.

1. `POST /api/chats/stream` (`Authorization`, `Accept: text/event-stream, application/json`, body `{question}`)
2. 응답이 401이면 재발급 후 1회 재시도, 그 밖의 오류 상태는 JSON 본문을 읽어 일반 오류로 처리 (스트림 시작 전 오류: 400 `INVALID_INPUT` · `NO_DOCUMENT`)
3. 본문을 읽으며 `createParser`가 이벤트 단위로 분리 → `sources` → `token`(반복) → `done` / `error`
4. `done` · `error`를 받으면 그 뒤 데이터는 무시하고 읽기를 끝냄

- 화면은 스트림 시작 전 오류(JSON)도 받기 위해 `application/json`을 함께 보낸다

| 이벤트 · 상황 | 화면 처리 |
|------|------|
| `sources` | 근거 자료 저장 (`documentId` · `documentName` · `page`만 남기고 형식 검사), 상태 `streaming` |
| `token` | `text`를 답변에 이어 붙임 |
| `done` | `chatId` 저장 → 피드백 활성. 거절 답변(공백 제거 후 80자 이하 + 거절 문구, `utils/refusal.js` — Backend와 같은 기준)이면 근거 자료 숨김 |
| `error` | 서버 `message` 표시 (없으면 고정 문구), 기록이 저장되지 않으므로 피드백 · 근거 자료 숨김 |
| `done` · `error` 없이 스트림 종료 | "답변이 중간에 끊겼어요. 다시 질문해 주세요." |
| 중단 버튼 · 메뉴 이동 | `AbortController`로 요청 취소 → 상태 `stopped`, "이 답변은 질문 기록에 저장되지 않아요" |
| 로그아웃 · 세션 만료 | 요청 취소, 화면의 메시지 전체 삭제 |
| `NO_DOCUMENT` | 오류 문구 + "내 자료로 가서 업로드하기" 링크 |

- 파서: 청크 경계에서 잘린 줄 이어 붙이기, `data:` 뒤 공백 유무 모두 처리, `\r\n` · 주석 줄(`:`) 처리, JSON이 아닌 `data`는 무시
- 동시에 1개 질문만 보낸다 (답변 중에는 입력 비활성). 화면 쪽 타임아웃은 두지 않고 서버 타임아웃을 따른다

### 7.2 오류 문구 변환 규칙

`utils/errorMessage.js`의 `errorMessage(err, map)`이 아래 순서로 문구를 고른다.

1. 응답 자체가 없음 (네트워크 오류 · 타임아웃) → "서버에 연결할 수 없어요. 잠시 후 다시 시도해 주세요."
2. 서버 공통 응답의 `message` (앞뒤 공백 제거, 최대 200자)
3. 화면별 map: `code` → HTTP 상태
4. 공통 기본 문구 `DEFAULTS` (400 · 401 · 403 · 404 · 429 · 500 · 503)
5. 그 밖의 상태 → 500 문구 "일시적인 오류가 발생했습니다"

| 상황 | 처리 |
|------|------|
| HTML 본문 (Nginx 기본 오류 페이지 등) | 본문으로 보지 않음 → 3 · 4 단계 문구 |
| 빈 본문 · `message` 없음 | 3 · 4 단계 문구 |
| 화면별 map | 로그인(`INVALID_CREDENTIALS` · 401, `ACCOUNT_LOCKED` · 423, 400), 회원가입(`DUPLICATE_EMAIL` · 409 · 400), 업로드(413 · 502 · 504) |
| 업로드 타임아웃 (`ECONNABORTED` · `ETIMEDOUT`) | "자료 처리 시간이 너무 오래 걸렸어요. 잠시 후 목록을 확인하거나 다시 시도해 주세요." |
| 423 잠금 | `data.lockedUntil`을 "11월 9일 오후 2:32까지 잠겨 있어요" 형식으로 함께 표시 |

- 스택 트레이스 · 내부 코드 등 서버 상세는 표시하지 않는다. 서버 `message`는 Backend가 사용자용으로 만든 문구

## 8. 주요 기능

| 기능 | 구현 |
|------|------|
| 반응형 디자인 | 헤더: 640px(`sm`) 이상은 한 줄(로고 · 메뉴 · 이메일 · 로그아웃), 640px 미만은 2줄(1줄 로고 · 이메일 · 로그아웃, 2줄 메뉴 3개). 메뉴 · 로그아웃 글자는 줄바꿈 금지(`whitespace-nowrap`), 이메일은 길면 말줄임(`truncate`) |

### 9.2 CSP · 보안 헤더

Nginx가 모든 응답(`always`)에 붙인다 (`frontend/nginx.conf`). 운영 서버 응답 헤더 확인 결과는 `9.보안점검서.md`에 기록한다.

| 헤더 | 값 |
|------|------|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `server_tokens` | `off` (Nginx 버전 미표시) |

- 화면은 외부 CDN · 외부 폰트를 쓰지 않는다 (시스템 폰트). 빌드 결과 `index.html`에는 인라인 스크립트 · 스타일이 없고 `/assets/`의 JS · CSS 파일만 불러온다
- **알려진 제한**: `style-src`에 `'unsafe-inline'`이 허용되어 있다
  - 소스에 인라인 `style=` 속성 없음 (검색 0건)
  - 질문 입력칸 높이 조절만 `el.style.height`로 바꾸며, DOM 조작이라 CSP 영향 없음 (`ChatInput`)
  - 빌드 결과 `index.html`에 인라인 style · script 없음
  - 값을 뺀 상태를 운영 환경에서 검증하지 않아 현재 값을 유지한다

### 9.3 토큰 저장 · 만료 처리

1. 로그인 성공 → Access Token · 회원 정보는 `authStore`(메모리), Refresh Token은 sessionStorage
2. 새로고침 → 메모리 값이 사라짐 → `restore()`가 Refresh Token으로 재발급 → 끝날 때까지 `ProtectedRoute` · `GuestRoute`는 로딩 표시
3. API 401 → 보낸 토큰이 아직 현재 토큰이면 `refresh()` 호출, 이미 다른 요청이 새 토큰을 받았으면 바로 재시도. 진행 중인 재발급 Promise를 함께 기다려 **동시 요청이 여러 개여도 재발급은 1번** (스트리밍 요청 포함)
4. 재시도는 요청마다 1회. 로그인 · 가입 · 재발급 요청 자체의 401은 재발급하지 않음
5. 재발급 실패 → 토큰 · 저장소 삭제 → 로그인 화면에 "세션이 만료되었어요. 다시 로그인해 주세요."
6. 로그아웃 → `POST /api/auth/logout`(Refresh Token 전달, 서버에서 폐기) → 401이면 재발급 후 1회 재시도 → 성공 · 실패와 관계없이 화면 토큰 삭제

### 9.4 로그아웃 · 계정 전환 시 스토어 초기화

이전 회원의 데이터가 다음 회원 화면에 보이지 않도록 한다 (`9.보안점검서.md` F-3 "계정 전환 시 이전 계정 데이터 없음").

| 스토어 | 처리 |
|------|------|
| `chatStore` · `documentStore` · `historyStore` | `useAuthStore.subscribe`로 `member`가 있다가 없어지면(로그아웃 · 세션 만료) `reset()` |
| `documentStore` · `historyStore` | `reset()` 때 `gen`을 올려, 로그아웃 전에 보낸 요청의 응답이 늦게 와도 반영하지 않음 |
| 진행 중 스트리밍 | 채팅 화면을 벗어나면(`AppLayout` 밖 로그인 화면으로 이동 포함) 요청 취소 |
| Refresh Token | `clear()`에서 sessionStorage 삭제 |

### 9.5 타임아웃 계층

안쪽(Backend)이 먼저 끝나고 바깥쪽(Nginx → 화면)이 더 길게 기다리도록 맞춘다. 바깥 계층이 먼저 끊으면 서버는 처리를 계속하는데 화면은 실패로 보기 때문이다.

| 요청 | 화면 | Nginx | Backend |
|------|------|------|------|
| 일반 API | 60초 (`api.js` `timeout: 60000`) | 별도 설정 없음 (Nginx 기본값) | - |
| 업로드 `POST /api/documents` | **180초** (`uploadDocument`만) | `proxy_read_timeout 150s` | 적재 120초 + 청크 삭제 10초 (`application.yaml` `ai.timeout`) |
| 답변 스트리밍 `/api/chats/stream` | 없음 (서버가 `error` 이벤트로 종료) | `proxy_read_timeout 120s` | 이벤트 간격 60초 (`stream-seconds`) |
| 토큰 재발급 | 60초 | 별도 설정 없음 | - |

### 9.6 알려진 제한

| 항목 | 내용 |
|------|------|
| Refresh Token sessionStorage 보관 | XSS가 생기면 읽힐 수 있음 → 텍스트 렌더링 · CSP로 방어, Refresh 회전. HttpOnly 쿠키는 CSRF 보호 · HTTPS가 함께 필요해 미적용 |
| 운영 HTTP(80) 평문 | 도메인 · 인증서 없음. 짧은 Access Token · Refresh 회전으로 완화 |
| 개발 의존성 취약점 | eslint 체인 moderate 4건, 운영 번들 미포함 · 수용 (F-5) |

- CSP `style-src 'unsafe-inline'` 허용: 알려진 제한
