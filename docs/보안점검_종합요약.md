# AskNote 보안 점검 보고서

**2026년 11월 10일 · 최종 배포 `main 641113f`**

팀이 수정한 회원 간 접근 제어를 최종 EC2에서 다시 확인했다. 다른 회원의 PDF 삭제 요청은 403으로 차단됐고, 질문에 다른 회원의 소유자·문서 ID를 넣어도 해당 자료가 답변이나 기록에 노출되지 않았다. 운영 로그인과 토큰 전송에는 HTTPS 적용이 남아 있다.

## 팀이 발견하고 수정한 취약점

| 발견한 문제 | 조치와 재확인 결과 |
|---|---|
| **다른 회원의 자료 삭제·피드백 수정**이 각각 204·200으로 성공했다. | 두 API에 소유자 검사를 추가했다. 타인 요청은 모두 403이 됐고, 수정 시도 후에도 원래 피드백 값이 유지됐다. |
| **RAG 검색 범위 조작**으로 다른 회원의 자료를 답변에 사용할 수 있었다. | 서버가 JWT 회원과 DB의 검색 가능 문서로 범위를 결정한다. 운영에서 A는 자기 PDF의 관측치 **347개**와 출처 1개를 받았다. B가 A의 ID를 넣자 답변이 거절됐고 저장된 출처는 0개였다. |
| **로그인·유료 AI 요청 횟수에 제한이 없었고**, 인증 구현에 계정 존재 추정 및 비밀번호 처리 문제가 있었다. | 로그인 5회 실패 후 15분 잠금(423), Nginx에 IP별 요청 제한을 적용했다. 운영에서 반복 인증 요청은 429였다. 없는 이메일도 BCrypt 비교를 수행하고, 로그인 시 72바이트 초과 입력은 401로 처리했다. 관리자 비밀번호 강도를 검사하고 기동 로그의 기본 계정 비밀번호 출력도 제거했다. |
| **AI 내부 API 명세가 노출**됐고, 501쪽 PDF도 전체 적재됐다. | 명세 경로 3개를 비활성화해 404를 확인했다. 본문 추출 전 쪽수를 검사해 501쪽은 422로 거부하고 500쪽은 정상 적재했다. |
| **컨테이너가 root로 실행**됐고, 베이스 이미지 버전이 빌드 시점에 따라 달라질 수 있었다. | 앱 3종을 비root로 실행하고 Linux 권한을 축소했다. 베이스 이미지는 버전과 digest로 고정하고 레지스트리 값과 대조했다. |
| **MariaDB JDBC 드라이버에서 취약점 4건**이 탐지됐다. | 3.5.10에서 3.5.11로 갱신했다. Backend 라이브러리 144개를 담은 SBOM 재검사에서 탐지는 0건이었다. |

## 최종 배포에서 남은 문제

| 확인 환경 | 관찰 결과 및 후속 조치 |
|---|---|
| **운영 EC2** | HTTP 80에서 서비스했고 443에는 연결되지 않았다. 실제 사용자 계정을 받기 전 HTTPS를 적용한다. 외부에서 3306·8000·8080에는 연결되지 않았다. |
| **최종 이미지 · 로컬 재현** | 위조한 `X-Forwarded-For`가 로그인 감사 IP로 기록됐다. 외부 요청을 직접 받는 Nginx에서 전달 IP를 실제 연결 주소로 덮어쓴다. 회원가입은 20자·74바이트 비밀번호에 500을 반환해 가입 단계에도 UTF-8 72바이트 검사가 필요하다. |
| **배포 설정 · 로컬 재현** | `IMAGE_TAG`가 비면 앱 3종이 `latest`를 선택했다. 태그 누락 시 배포를 중단하도록 한다. Backend IP 변경 후 Nginx가 이전 주소로 연결해 502가 발생했고, Nginx 재시작 후 정상화됐다. 배포 절차에 upstream 갱신과 인증 경로 검증을 포함한다. |
| **최종 이미지 · Trivy** | HIGH / CRITICAL 탐지는 Frontend **9 / 1**, Backend **2 / 0**, AI **51 / 2**로 이전 태그와 동일했다. 패키지별 탐지 건수이며, AI에는 ChromaDB 고유 CVE 4건이 포함된다. |

**확인 범위**　운영 프런트엔드 번들은 최종 이미지와 SHA-256이 일치했다. EC2에서 실행 중인 Backend·AI의 digest, 서버 내부 보안 설정과 운영 LLM 키 권한·비용 한도는 담당자 확인이 남았다.
